Council · acme/shop-api #142 — rate-limit the public API per account with a token bucket

Single PR, ready for review, on main · head 5d1e0c9b · reviewed 2026-10-01

High level contextThe public API has no limit on how often a caller may send requests, so one misbehaving integration can slow the service for every other account. This PR adds a token-bucket limiter in front of every public route: each account may burst 20 requests and then refills at 5 per second. A request with no tokens left receives a 429 response with a Retry-After header. Bucket state lives in Redis so that every API instance shares one count per account.

Is this the right direction?Yes. A shared per-account limit is the standard answer to one noisy caller degrading everyone, and a token bucket allows the short bursts that real integrations produce. The open question is not the limiter but what happens when Redis is unavailable, because the PR silently chooses to reject every request. That is card #1.

Primer — what this review assumed you knew

Token bucket

what it isA token bucket is a rate limit that allows short bursts while holding a steady average. Each account has a bucket holding up to 20 tokens. Every request spends one token, and the bucket refills at 5 tokens per second. A request that finds the bucket empty is rejected.

where it livesThe limiter lives in src/middleware/rateLimit.ts:18.

why it mattered hereCards #1 and #2 depend on where the bucket is read and written. A count that two requests read at the same moment can let both spend the same token.

read nextThe linked rate-limit doc states the limits promised to API customers.

Fail open and fail closed

what it isA protective check must decide what to do when it cannot run. Failing open lets the request through unchecked. Failing closed rejects the request. This codebase's other Redis-backed checks, such as the idempotency cache, fail open and log a warning.

where it livesThe existing convention lives in src/middleware/idempotency.ts:40.

why it mattered hereCard #1 asks which way the new limiter should fail. The PR chooses differently from the rest of the codebase without saying so.

Findings

Do before merge

#2Two requests arriving together can both spend the last token

subtle bugsconcurrency
Context
Every API instance reads an account's token count from Redis, decides whether the request may proceed, and writes the new count back.
Where
src/middleware/rateLimit.ts:31
Finding
The read and the write are two separate Redis commands with nothing tying them together. Two instances that read the count at the same moment both see one token left, both admit their request, and both write zero. Under a burst the limit is therefore exceeded by up to one request per instance. Production runs twelve instances, so a caller can briefly reach thirty-two requests where the promise is twenty.
Recommendation
Move the read, the refill, and the spend into one Lua script run with EVAL, so Redis performs the whole decision as a single step.
Fix size
One Lua script and one call site.

#3The Retry-After header is in milliseconds where clients expect seconds

api compatibility
Context
A rejected request carries a Retry-After header telling the client how long to wait before trying again.
Where
src/middleware/rateLimit.ts:52
Finding
The header is set to the refill delay in milliseconds, so a client told to wait 200 milliseconds reads the value as 200 seconds. The HTTP standard defines the value in seconds, and the common client libraries follow it. A well-behaved integration would therefore stall for minutes after every rejection.
Recommendation
Divide the delay by 1,000 and round up, and assert the header value in the existing rejection test.
Fix size
One expression and one assertion.

Decide

#1When Redis is unavailable, every public request is rejected

premiseoperational hardening
Context
The limiter needs Redis to read the bucket. Other Redis-backed checks in this codebase let requests through when Redis cannot be reached.
Where
src/middleware/rateLimit.ts:24 · src/middleware/idempotency.ts:40
Finding
A Redis error is caught and turned into a 429 response. A Redis outage therefore becomes a full API outage, which is worse than the noisy-caller problem the PR sets out to solve. The PR body does not mention this choice, and it contradicts the convention the idempotency cache already follows.
Recommendation
Decide which way the limiter fails. Failing open matches the codebase and keeps the API up during an outage, at the cost of no limit while Redis is down. If failing closed is intended, state it in the rate-limit doc and add an alert on the error path.
Fix size
One branch in the error handler, or one doc paragraph and one alert.
Judgement call
If the team prefers rejecting traffic to running unprotected, the current behavior can stay once it is documented.

#4Internal service calls share the customer limit

premise
Context
The admin dashboard calls the public API with a service account to load customer data.
Where
src/middleware/rateLimit.ts:19
Finding
The limiter applies to every account, including the dashboard's service account. Opening a busy customer page sends about forty requests at once, so the dashboard would receive 429 responses on ordinary use.
Recommendation
Exempt service accounts by their existing role, or give them a higher limit through the same configuration.
Fix size
One condition on the account role.
