Council · acme/shop-api #142 — rate-limit the public API per account with a token bucket

Single PR on main · head 5d1e0c9b · reviewed 2026-10-01

High level contextThe public API has no limit on how often a caller may send requests, so one misbehaving integration can slow the service for every account. This PR puts a token-bucket limiter in front of every public route. Each account may burst 20 requests and then refills at 5 per second. Bucket state lives in Redis, so every API instance shares one count per account.

Is this the right direction?Yes. A shared per-account limit is the standard answer to one noisy caller slowing everyone, and a token bucket allows the short bursts real integrations produce. The open question is what happens when Redis is down, which is card #3.

#1Two requests arriving together can both spend the last token

Under a burst, a caller can briefly get past the limit by one request per API instance.

correctnessassumes: token bucket
Comment

Lands on src/middleware/rateLimit.ts:31

Can two instances both read the last token here before either one writes it back? If so, a burst could slip one extra request per instance past the limit.
This feels like it wants to be one atomic step in Redis. I'd advocate we move the read, refill and spend into a single Lua script so a token can't be spent twice.
Evidence
Context
Every API instance reads an account's token count from Redis, decides whether the request may proceed, and writes the new count back.
Where
rateLimit.ts:22 · rateLimit.ts:31
Finding
The read and the write are two separate Redis commands with nothing tying them together. Two instances that read at the same moment both see one token left and both admit their request. Production runs twelve instances, so a caller can briefly reach thirty-two requests where the promise is twenty.
Recommendation
Move the read, the refill and the spend into one Lua script run with EVAL, so Redis makes the whole decision in a single step.
Fix size
One Lua script and one call site.
Reply
The author may say one extra request per instance is harmless. The doc promises twenty, though, and the fix is small.

#3When Redis is unavailable, every public request is rejected

A Redis outage would become a full API outage, which is worse than the noisy caller this PR sets out to stop.

designsafetyassumes: fail open and fail closed
Comment

Lands on src/middleware/rateLimit.ts:25

Is there intentionality behind rejecting everything when Redis can't be reached? The idempotency cache lets requests through in that case, so this looks like the one place that fails the other way.
I'd wonder if we want this to fail open like the idempotency cache, so a Redis outage doesn't take the API down with it. If failing closed is the intent, perhaps worth saying so in the rate-limit doc with an alert on this path?
Evidence
Context
The limiter needs Redis to read the bucket, while other Redis-backed checks here let requests through when Redis is down.
Where
rateLimit.ts:25 · idempotency.ts:40
Finding
A Redis error is caught and turned into a 429 response. A Redis outage therefore rejects every public request. The PR body does not mention this choice, and it differs from the idempotency cache.
Recommendation
Decide which way the limiter fails. Failing open matches the codebase and keeps the API up, at the cost of no limit during the outage. Failing closed needs a doc line and an alert.
Fix size
One branch in the error handler, or one doc paragraph and one alert.
Judgement call
If the team prefers rejecting traffic to running unprotected, the current behavior can stay once it is documented.
Reply
The author may say failing closed is safer. That is a fair position, and the card only asks that it be stated.
